# 串门走自己的端口，不挂 DSH 的 webserver

## Status

accepted

## 背景

DSH 的 `ctx.webServer` 可以把路由挂到 GUI 同一个端口上，而且它本来就支持绑局域网地址（`--host 10.0.0.7`）。看起来是最省事的路。

但是：那个端口前面有一道**浏览器信任闸门**——loopback `Host` 才被接受，除非把对方地址写进 `--trusted-host`；写进去之后，对方就拿到了对 DSH API 的访问权。也就是说，"允许同事看见我的宠物"会被迫变成"允许同事访问我的 DSH"。

## 决定

插件 Host 半边自己监听一个端口（UDP 用于发现和心跳，TCP 用于串门请求），与 DSH 的 webserver 完全无关。它有自己的信任模型（首次见面放行），自己的速率限制，自己的关闭开关。

## 考虑过的选项

- **挂 `/local-pet/*` 到 DSH webserver**：零新增端口、零新增生命周期，但把宠物开关和会话访问权绑在一起。放弃。
- **走 DSH 的 Peer/principal 模型**：`ctx.remoteAccess` 确实已经能表达"非 owner 的 principal"。但它服务的是"浏览器访问本机 DSH"，不是"两台机器平级对话"，套上去反而更重。

## 一处必要的细分

"串门流量不走 DSH 的端口"和"本地页面怎么读到客厅状态"是两个问题。已经在 DSH 页面里的浏览器，读客厅快照走的是 DSH 自己的 webserver 路由（同源、带已有 cookie、不需要 CORS、不需要第二个口令）；那上面的请求本来就被 DSH 的信任闸门挡在 loopback 之外。**只有机器与机器之间的流量**才走我们自己那个端口。这个细分不允许被扩大成"为了省事把串门端点也挂上去"。

## 后果

- 用户要在防火墙里放行一个端口（本机 macOS 会弹一次"允许传入连接"）。
- 串门数据与 DSH 会话数据在物理上隔离：谁攻破串门端口，也摸不到 DSH 的 API。
- 插件运行时**没有沙箱**（插件进程即用户进程），所以"不可信输入"这层防线必须由协议自己扛：远端字段只允许产生渲染和一条串门记录，绝不触发文件写入、命令执行或本机状态读取。
