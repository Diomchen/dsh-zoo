# 1.3.0-test.6 · 「这位邻居已经不在桌面上了」是怎么来的

现场（Windows，`1.3.0-test.5`）：**每一位**邻居的农场都弹红色提示「这位邻居已经不在桌面上了」——
右键小街上那户房子、或在农场窗里点邻居小圆片，都一样。同一台机器上
`POST /dsh-zoo/action {"action":"farm-look","deviceId":"<那位邻居>"}` 却成功（`ok:true`、`window:"opened"`）。

## 原因：helper → 宿主这一跳把 `deviceId` 削成了 null

同一条 `farm-look` 要过 **两道**白名单，是**两个进程边界**：

| 跳 | 代码 | 票 54 之后 |
| --- | --- | --- |
| 渲染端 → Electron 主进程 | `desktop/main.js:901` 的 `needsDevice` | 含 `farm-look` / `farm-raid` ✅ |
| helper → 宿主 | `desktop/shared.js` `normalizeHelperEvent` 的 `needsDevice`（`src/desktop.js:418` 调） | 只有四个旧动作 ❌ |

第二道不认识这两个动作，`deviceId` 就被置成 `null`，而且因为「不在它的 needsDevice 里」连
`bad-device-id` 都不报，静默放行。宿主 `handleDesktopAction` 于是拿到 `undefined` →
`lookAtNeighborFarm(undefined)` → `bad-device-id` → `desktopActionNotice`
（`src/service.js`）：**「这位邻居已经不在桌面上了。」**

HTTP 口（`handleActionInner`）直接读 `body.deviceId`，不经过这个 normalizer——所以「curl 通、UI 不通」。

两条入口都走同一跳：农场窗的 `dsh-zoo:farm-submit` 最终也是 `writeEvent({...action, type:'action'})`
（`desktop/main.js` 的 `startFarmPending`），所以小圆片和右键一起坏。

## 修法

「必须有对象」的动作只留一份：`desktop/shared.js` 的 `DEVICE_ACTIONS`
（`end-visit` / `admit` / `reject` / `dismiss` / `farm-look` / `farm-raid`），
`main.js` 与 `normalizeHelperEvent` 都用它。缺对象的看田/偷菜现在整条拒（`bad-device-id`），
不再静默变成「邻居不在了」。

## 回归测试

`test/farm-look-helper.test.js`：从 **helper 真正写出的那一行**开始，走宿主同一个
`parseLine → normalizeHelperEvent`，再喂给真 service + 真双宠物，断言开出来的是 `mode:'look'` 的窗、
不是那句话。只测 `normalizeFarmAction`（农场窗那条窄口）会让这个 bug 绿着出厂。

## Windows 验收

1. `certutil -hashfile dsh-zoo-1.3.0-windows-test.6.tgz SHA256`
   = `baf4872b4e00a4d088ab378f894db052a99301dfa86e755cfea7d697d7f226e6`
2. 解包后 require 里面那份 `shared.js`，三条必须都对：
   - `farm-look` + 合法 `deviceId` → `deviceId` 原样保留
   - `farm-raid` + 合法 `deviceId` → 同上
   - `farm-look` 不带 `deviceId` → `{"ok":false,"error":"bad-device-id"}`
3. `pnpm add` 装上，`version` = `1.3.0-test.6`；**重启 DSH** 后：
   - 右键邻居房子 → 直接开出「某某的农场」只读窗（不再弹「不在桌面上」）
   - 农场窗里点别的邻居小圆片 → 正常切到那一家
   - 看田窗底部「派它去偷」能发出去（同一跳，同一个字段）
