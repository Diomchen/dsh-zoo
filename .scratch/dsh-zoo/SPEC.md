# SPEC · dsh-zoo（局域网 DSH 宠物串门）

## Problem Statement

DSH 里每台机器各养一只宠物，但它们彼此看不见：隔壁工位那位同事的宠物对我不存在，我的宠物也走不出我这台机器。宠物成了一个死掉的装饰品——打开 DSH 只知道"我有个宠物"，不知道"我们有几个宠物"。

而串门恰恰是这件事唯一有趣的用法：它不需要聊天、不需要协作，只需要"它真的过去了"。

## Solution

一个 DSH 插件，在 GUI 里开一块**客厅**浮层。打开 DSH 五秒内，客厅里出现同网段其他实例的**邻居灯**；第一次见面问一句要不要放行，放行之后对方的宠物作为**访客**出现在我的客厅里，动作跟着对方走。我也可以把自己的宠物拖到邻居灯上，让它出门去对方家待一分钟，到点自己走回来，双方各留一条**串门记录**。

本地宠物仍然是现有的 `dsh-pet` 那只，插件不接管它——只借它的外观素材和当前动作。

## User Stories

1. 作为 DSH 用户，我想在打开 DSH 后五秒内看到同一局域网里还有谁在养宠物，这样我不用填任何地址就知道"有人在线"。
2. 作为 DSH 用户，我想看到邻居的名字而不是 IP 地址，这样我知道那是谁。
3. 作为 DSH 用户，我想在第一次遇到某个邻居时被问一句"要不要让它进来"，这样陌生机器不能直接往我屏幕上放东西。
4. 作为 DSH 用户，我想在被问过之后不再被问，这样串门没有每次都点确认的摩擦。
5. 作为 DSH 用户，我想在拒绝某个邻居之后它不再出现，这样我可以让不想看见的人消失。
6. 作为 DSH 用户，我想看见被我放行的邻居的宠物在我的客厅里活动，这样"对方也在线"这件事是可见的。
7. 作为 DSH 用户，我想让访客的动作跟着对方真实动作走，这样它是活的，不是一个贴图。
8. 作为 DSH 用户，我想在对方关掉 DSH 之后看到访客淡出，而不是僵在原地，这样我知道它走了。
9. 作为 DSH 用户，我想把我自己的宠物拖到邻居灯上就能让它出门，这样串门是一个动作而不是一层菜单。
10. 作为 DSH 用户，我想在宠物出门后看到它"在别人家"的状态，而不是从客厅里凭空消失。
11. 作为 DSH 用户，我想在它出门一分钟后自动回来，这样我不必记得去接它。
12. 作为 DSH 用户，我想随时把它召回来，这样我改主意时不用等。
13. 作为 DSH 用户，我想在对方没放行我时得到一句明确的失败，而不是宠物静悄悄没动。
14. 作为 DSH 用户，我想在串门发生时双方各留一条记录，这样"它上周来过"是可查的。
15. 作为 DSH 用户，我想点一下访客就看见最近五条串门记录，这样我不用打开一个历史页面。
16. 作为 DSH 用户，我想让客厅不挡住 DSH 的主界面，这样我不必为了养宠物牺牲工作区。
17. 作为 DSH 用户，我想在没装 `dsh-pet` 时看到一行解释而不是白屏，这样我知道少了什么。
18. 作为 DSH 用户，我想在邻居的素材对不上时看到一只带名字的色块，而不是空白，这样它还在场。
19. 作为 DSH 用户，我想让客厅里的邻居灯最多只占一条窄边，这样六个人在线时我也不被淹没。
20. 作为 DSH 用户，我想在完全断网时客厅仍然显示我自己的宠物，这样插件坏掉时我还能看出是网络问题。
21. 作为关心隐私的用户，我想确认协议只送名字、外观和动作，绝不送项目名、文件路径或会话内容。
22. 作为用户，我想能一键关掉"允许别人把宠物派到我这"，这样开会投屏时不用解释。
23. 作为用户，我想重启 DSH 之后邻居名单、放行记录和串门记录都还在，这样每天不用重新认识同事。
24. 作为开发者，我想让协议带着版本号，这样两边版本不一致时是"忽略"而不是"诡异行为"。

## Implementation Decisions

**形态**：一个 npm 包，两个半边。Host 半边是 Node，负责身份、发现、信任、串门、记录；Client 半边是一个没有构建步骤的 classic script，只负责画客厅。Client 通过 HTTP 读 host 的客厅快照（沿用 `dsh-pet` 证明过可行的单调计数器 + 轮询），写操作走同一组端点。

**客厅的位置**：GUI 的 `shell.overlay` 浮层槽位，用一个新 id 加进去，不替换任何现有条目。整层点穿，只有宠物本体、邻居灯、邻居弹层、访客、串门卡片和串门开关接收指针事件。v1 不做桌面层（见 ADR-0004）。

**身份**：`deviceId` 是随机 UUID，存在本机 `$DSH_HOME/dsh-zoo/` 下的 identity 文件里；昵称默认取本机第一只 `dsh-pet` 宠物的名字，没有则取主机名。重置身份 = 删这个文件。不复用 `~/.dsh/.anonymous-user-id`（它明确不与设备绑定，且语义是"匿名用户"）。

**发现**：UDP 广播，固定端口，每 5 秒一次；收到广播即单播回执。广播包只含协议版本、`deviceId`、昵称、监听端口。没有 mDNS 可用，也不引入依赖。

**发现之后**：未放行的邻居只出现在"待放行"列表里，本机不向它发送任何心跳。

**心跳**：放行之后每 2 秒一次 UDP 心跳，只载当前动作名（`anim`）。原计划的朝向与“是否被拖拽”没有实现：客户端只按动作名选素材，没有消费者；拖拽是纯本机交互，按 ADR-0003 不上网。30 秒无心跳 → 访客淡出，记录保留。

**坐标永不过网**（见 ADR-0003）。访客在本机自己跑物理。

**串门**：复用现有 UDP socket，不另开 TCP 监听。四种报文——`visit-request` / `visit-ack` / `visit-deny` / `visit-recall`：拖到邻居灯上发请求，请求最多发三次（约 600ms 间隔），拿到 ack 才算抵达；约 1.8 秒没有 ack 就明确超时。宠物出门后有 60 秒 TTL，到期由发起方主动召回；接收方在 TTL 到期后也自行清理，不依赖对方守约。失败永远是一句可读的提示，不是静默无反应。（原计划的 TCP 单次请求/响应在实现时改为 UDP：第二个监听端口意味着第二个要广播的端口和第二条信任路径；重试 + 明确失败已经提供了同等的“到底到没到”的确定性。见 `docs/protocol.md`。）

**串门开关**：客厅里有一个一键开关，默认“允许串门”，状态落在 `<dataDir>/settings.json`，重启后保持。关掉后只拒入站 `visit-request`（回一条带 `visits-off` 理由的 `visit-deny`，发起方看到“对方关掉了串门”），邻居灯、心跳与本机出门都不受影响。

**信任存储**：`$DSH_HOME/dsh-zoo/` 下的 peers 文件，记 `deviceId`、昵称、放行时间；拒绝过的另记一份拒绝名单，不再提示。全部是本机文件，可手改、可删。

**串门记录**：同一目录下的 visits 文件，滚动上限 200 条，超出丢最旧的。卡片读最近 5 条。

**协议**：每条报文都有版本号与类型；版本不匹配的报文被忽略并只记一条日志。JSON 编码，单包上限 4 KiB，字段白名单，字符串截断到定长。未知字段直接丢弃，不报错、不转发。

**不可信输入的边界**（这是 ADR-0002 的配套约束，必须由实现强制）：远端字段只能产生两种效果——改变渲染，和写一条串门记录。不得触发文件写入（除上述两个有界文件）、不得触发命令执行、不得读取本机状态回传、不得让报文内容进入日志以外的任何路径。每来源限速，超限丢弃而非排队。

**素材**：访客用 `dsh-pet` 已有的素材路由，按动作名取同一段视频。取不到（404 / 名字不认识）→ 退到 idle；仍然取不到 → 一个带名字的色块。协议永不传素材本体。

**降级**：`dsh-pet` 不存在 → 客厅显示一行说明；网络不可用 → 客厅只有本地影子；两者都坏 → 一行说明。

**本地影子**：客厅里也画一只"我自己"，跟随 `dsh-pet` 当前动作。这不是第二只宠物，是同一只在另一块屏幕上的呈现；宠物出门期间它显示为"出门了"。

## Testing Decisions

好测试只断言外部行为：给了什么报文、在什么时刻，客厅里应该有什么、该发出什么包。不断言内部结构、不测 DOM、不测物理和动画播放（那是 `dsh-pet` 的事）。

三个层次，只有一个新建 seam：

1. **协议内核**（主 seam，也是唯一的新 seam）：一个纯状态机——`(当前状态, 事件, 现在时刻) → (新状态, 要执行的效果)`。事件是收到一个报文、心跳超时、用户点了放行、用户拖了宠物。效果是"发出这个包""写这条记录""现在客厅里应有这些宠物"。这一层覆盖发现、信任、串门生命周期、限速、版本不匹配、TTL 过期。测试是一个脚本化的时间线，不碰 socket。
2. **Host 集成**：两个 host 实例跑在回环的不同端口上，走真实 UDP，验证"发现 → 放行 → 串门 → 召回 → 记录"整条链。这一层不碰 UI，是 `dsh-pet` 那类插件唯一可行的端到端验证。
3. **客厅视图（没有纯视图模型）**：浏览器半边必须保持为一个没有构建步骤的 classic script，视图判断（选哪段素材、404 怎么降级、访客怎么淡出、弹层开合）只能写在 `client.js` 里，抽不出可单独测试的纯函数，也不值得为此引入打包器。它只有 `node --check client.js` 的语法检查与手工验收；测试真正钉住的是宿主快照的形状与语义——那是视图唯一的输入契约。

第一层用脚本时间线驱动，不依赖真实等待；第二层的双实例回环端到端用例会轮询墙钟，因为真实 UDP socket 的时序没法用假时钟替代（这是有意的例外，其余用例仍用注入的短间隔）。第三层完全不碰浏览器。

## Out of Scope

- 桌面层浮窗（v1 明确不做，见 ADR-0004）
- 跨网段、公网、NAT 穿透、中继
- 素材传输（只传动作名）
- 加密与密钥交换（v1 明文，信任模型是同网段 + 首次放行）
- 每台机器多只宠物（v1 一只）
- 移动端、命令行界面
- AI 对话、表情包、余额、投喂（都是 `dsh-pet` 已有的，不重复）
- 串门历史的独立页面

## Further Notes

- **已知体验缺口**：用户平时看的是桌面层的宠物，而 v1 的客厅在 GUI 里。做完必须当面演示一次"打开 GUI 才看得见"，确认这个缺口可以接受，再谈桌面层。
- **依赖风险**：`dsh-pet` 的 HTTP 接口是未承诺接口。适配层必须薄，且协议里不出现它的数据结构。
- **防火墙**：macOS 首次监听会弹"允许传入连接"，这属于一次性设置，写进 README。
- **六个人在线**：客厅同屏最多 4 位访客，其余折进边缘的邻居条；放行与串门都在邻居条上操作。
- **协议文档**：报文形状一旦确定就写进 `docs/protocol.md`，包括"坐标永不过网"和"未知字段直接丢弃"这两条，防止后来者把它们当成遗漏来"修"。
